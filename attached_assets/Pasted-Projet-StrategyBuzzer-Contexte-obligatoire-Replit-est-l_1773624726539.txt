Décision d’architecture à respecter
Ne pas copier la structure Solo 4 fois.
Ne pas maintenir un gameplay dupliqué entre Duo et Ligue.
Construire une base commune unique.

Cible
1 moteur commun
1 famille d’écrans commune
4 variantes spécialisées :
- Solo
- Duo
- Ligue
- Maître du jeu

Objectif de structure
A. Base commune de présentation
Utiliser la famille `game_*` et `unified_tiebreaker_*` comme base premium commune pour :
- question
- réponse
- résultat
- saviez-vous
- transition
- fin de match
- avant tiebreaker
- tiebreaker

B. Spécificités de mode
Conserver des wrappers / extensions propres pour :
- Duo : adversaire, buzz adverse, chat, audio live, skills adverses, synchronisation temps réel, mise
- Ligue : classement, divisions, rewards saison, logique compétitive, équipe/individuel
- Solo : progression, niveau, vies, IA, boss
- Maître du jeu : contrôle manuel des phases, grand lobby, animation de groupe

C. Runtime commun
Le moteur gameplay ne doit pas être dans Blade.
Le runtime doit être piloté par :
- apps/game-server/src/services/GameOrchestrator.ts
- packages/game-engine/src/state-machine.ts

D. Providers de mode
Les différences de mode doivent être portées par une couche de provider/configuration, pas par dupliquer tout le gameplay :
- app/Services/SoloGameProvider.php
- app/Services/DuoGameProvider.php
- app/Services/LeagueGameProvider.php
- plus tard un provider Maître du jeu si nécessaire

Boucle gameplay commune à supporter
Tous les modes doivent pouvoir partager ce squelette :
- MATCH_INTRO
- ROUND_INTRO
- QUESTION_DISPLAY
- BUZZ_OPEN
- ANSWER_WINDOW
- ANSWER_LOCKED
- ROUND_RESULT
- ROUND_TRANSITION
- TIEBREAKER_INTRO
- TIEBREAKER_QUESTION
- MATCH_RESULT
- MATCH_FINISHED

Règles produit obligatoires
1. Le “Saviez-vous ?” est obligatoire après chaque question dans la page résultat
2. Les avatars stratégiques sont choisis avant le match
3. Les skills doivent être pris en compte dès la première question
4. Les skills sont contextuels à la phase
5. Une icône de skill peut apparaître à des emplacements différents selon la page
6. Une icône peut s’illuminer seulement quand la condition serveur devient vraie
7. Le client n’envoie qu’une intention d’activation de skill
8. Le serveur valide et applique
9. Le serveur décide seul :
   - buzz
   - score
   - réponse acceptée
   - activation de skill
   - effet adverse
   - tiebreaker
   - transitions
   - fin de match
10. Les entre-manches doivent être synchronisées
11. Le tiebreaker doit être piloté côté serveur
12. Le chat et l’audio ne doivent jamais casser la synchro
