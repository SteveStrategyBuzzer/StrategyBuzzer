## 1. CURRENT_KERNEL_RECEIVED ne suffit pas à autoriser le Blueprint suivant

Tu as écrit :

CURRENT_KERNEL_RECEIVED
→ fermeture confirmée du Blueprint courant
→ autorisation de créer le prochain Blueprint

Cette règle est incomplète.

ReadyBank et Taxonomy fournissent deux confirmations indépendantes.

### Confirmation 1 — ReadyBank

CURRENT_KERNEL_RECEIVED confirme :

* que le Blueprint canonique courant a été reçu ;
* que ce Blueprint n’est plus en circulation ;
* que son noyau peut être comptabilisé de manière idempotente.

Effets :

kernel_received_total[depth][domain] += 1

Blueprint courant
→ RECEIVED / CLOSED

### Confirmation 2 — Taxonomy

Taxonomy doit fournir l’état du réservoir concerné après la consommation du noyau courant :

AVAILABLE

ou :

EMPTY

Cette information permet à KernelRotationPlanner de savoir :

* si le même domaine peut encore participer à la rotation ;
* si ce domaine doit être ignoré pour le reste du tour ;
* si les huit domaines sont maintenant EMPTY ;
* si le tour du Depth peut être fermé.

## 2. Barrière complète avant le Blueprint suivant

La création du Blueprint suivant est autorisée seulement lorsque :

CURRENT_KERNEL_RECEIVED reçu
+
état Taxonomy du réservoir courant reçu
+
aucun Blueprint encore en circulation

Alors KernelRotationPlanner peut :

* poursuivre vers le prochain domaine AVAILABLE du même Depth ;
* ou fermer le tour si les huit domaines sont EMPTY ;
* ou passer au prochain Depth requis après fermeture du tour.

La règle correcte est donc :

READY_BANK_CONFIRMED
+
TAXONOMY_STATE_READY
→ décision de rotation suivante autorisée

Jamais :

CURRENT_KERNEL_RECEIVED seul
→ prochain Blueprint automatiquement autorisé

## 3. Séparation des responsabilités

CURRENT_KERNEL_RECEIVED répond à la question :

« Le Blueprint canonique courant a-t-il été reçu et fermé ? »

Taxonomy répond à la question :

« Le réservoir de ce domaine possède-t-il encore un noyau disponible ? »

KernelRotationPlanner combine ces deux réponses pour décider :

* prochain domaine du même Depth ;
* fermeture du tour ;
* changement de Depth ;
* mise en attente globale.
