# STRATEGYBUZZER — SPÉCIFICATION FONCTIONNELLE COMPLÈTE

## Brique : KernelRotationPlanner

## Phase : Implémentation Rotation après Blueprint Phase 0 validé

---

# 1. Objectif

Implémenter **KernelRotationPlanner** sans modifier le contrat Blueprint validé.

KernelRotationPlanner est la première brique décisionnelle après le Blueprint.

Il sert uniquement à déterminer le prochain contexte de rotation d’un noyau.

Il produit exclusivement :

* `depth_slot`
* `domain_slot`
* `rotation_identifier`

Il ne produit rien d’autre.

---

Ne pas extrapoler.

Ne pas inventer :

* nouvelle brique ;
* nouveau statut ;
* nouvel événement ;
* nouveau mécanisme d’écriture ;
* nouveau format de `kernel_code` ;
* nouveau comportement Taxonomy ;
* nouvelle logique READY_BANK ;
* nouvelle logique gameplay.

Si une information n’existe pas dans le code réel :

```text
BLOCAGE — contrat non couvert par le code actuel
```

Puis expliquer précisément ce qui manque.

# 4. Valeurs officielles de production par depth

La banque de noyaux doit viser les volumes suivants :

```text
Depth 4 : 3000 noyaux
Depth 6 : 3000 noyaux
Depth 7 : 2500 noyaux
Depth 8 : 2000 noyaux
Depth 9 : 1500 noyaux
```

Total cible v1 :

```text
12000 noyaux
```

Ces valeurs sont des cibles de noyaux, pas des questions finales.

Un noyau pourra ensuite produire plusieurs objets en aval selon Phase 1, mais KernelRotationPlanner ne gère pas cela.

# 6. DepthNeedMatrix

## Rôle

DepthNeedMatrix ne choisit jamais la profondeur.

DepthNeedMatrix fournit uniquement une matrice des besoins par depth.

## Structure attendue

```text
DepthNeedMatrix
- depth
- target_kernels
- existing_kernels
- remaining_kernels
- completed
```

Exemple :

```text
Depth 4 : target 3000 / existing 3000 / remaining 0 / completed true
Depth 6 : target 3000 / existing 0 / remaining 3000 / completed false
Depth 7 : target 2500 / existing 0 / remaining 2500 / completed false
Depth 8 : target 2000 / existing 0 / remaining 2000 / completed false
Depth 9 : target 1500 / existing 0 / remaining 1500 / completed false
```

## Source actuelle autorisée

Utiliser le code existant si possible :

```text
BankNeedsCalculator
config/question_bank_profiles.php
```

Ne pas créer une nouvelle classe `DepthNeedMatrix` si `BankNeedsCalculator` peut fournir la couverture nécessaire par adaptation minimale.

---

# 7. Règle de choix de depth

KernelRotationPlanner lit DepthNeedMatrix.

Il choisit UNE seule profondeur.

Règle v1 :

```text
Choisir le depth autorisé ayant le plus grand remaining_kernels.
```

En cas d’égalité :

```text
choisir le depth le plus bas.
```

Exemple :

```text
Depth 6 : remaining 3000
Depth 7 : remaining 2500
Depth 8 : remaining 2000
Depth 9 : remaining 1500

=> KernelRotationPlanner choisit Depth 6.
```

Si tous les `remaining_kernels` sont à 0 :

```text
STOP — aucune profondeur à produire
```

Aucun fallback.

---

# 8. DomainCycle

## Rôle

DomainCycle fournit le domaine actif selon une rotation stricte.

KernelRotationPlanner choisit UNE seule valeur pour `domain_slot`.

## Domaines officiels v1

Utiliser uniquement les domaines présents dans la configuration réelle.

Si la config contient cette liste :

```text
general
histoire
sport
geographie
art
cuisine
science
cinema
faune
```

alors c’est la liste utilisée.

Ne pas inventer de domaine.

## Règle de rotation domaine

Règle v1 :

```text
À chaque nouveau noyau, passer au domaine suivant dans l’ordre officiel.
```

Si on arrive à la fin :

```text
revenir au premier domaine.
```

Aucun saut.

Aucune optimisation.

Aucune heuristique.

Aucun choix IA.

---

# 9. rotation_identifier

KernelRotationPlanner produit `rotation_identifier`.

Règles :

```text
rotation_identifier n’est pas kernel_code.
rotation_identifier n’est pas kernel_code_prefix.
rotation_identifier n’est pas un fragment du futur kernel_code.
rotation_identifier n’a aucun format métier imposé.
rotation_identifier doit seulement être unique dans le périmètre de rotation.
```

Format technique accepté v1 :

```text
UUID
```

Si un générateur UUID existe déjà dans le projet, l’utiliser.

Sinon utiliser le mécanisme Laravel standard disponible.

Ne pas utiliser `yy-xx`.
