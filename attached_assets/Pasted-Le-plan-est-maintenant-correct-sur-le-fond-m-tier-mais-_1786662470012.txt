==================================================

La séquence :

résolution
→ gate
→ création Blueprint
→ application depth/domain
→ mise à jour domain_position / active_depth

doit être atomique par rapport au RotationState.

Proposition privilégiée :

BEGIN TRANSACTION

  lock kernel_rotation_state_v2 FOR UPDATE

  KRP resolveNextRotation()
  sur CET état verrouillé

  si NoRotation :
      COMMIT
      Factory NON appelée
      return

  Factory::create()
  → Blueprint existe maintenant

  KRP applyRotation()
  → utilise exactement la résolution calculée sous le même lock
  → fillRotation(depth, domain)
  → écrit active_depth
  → écrit domain_position
  → écrit active_blueprint_identity

COMMIT

En cas d'exception à n'importe quelle étape :

ROLLBACK COMPLET

Ainsi :

- aucun Blueprint orphelin ;
- aucune résolution stale ;
- aucun deuxième sélecteur ;
- Blueprint existe toujours avant fillRotation ;
- Factory ne connaît toujours pas KRP ;
- KRP reste propriétaire de la sélection ;
- orchestration reste propriétaire du gate/cycle.
