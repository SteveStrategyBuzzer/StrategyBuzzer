===========================================================
CORRECTION 1 — KLD reste un moteur métier pur
===========================================================

KEY_LEARNING_DIRECTION ne doit pas interroger directement :

- QuestionIntent
- Eloquent
- DB
- question_intents
- migrations

Donc supprimer du document :

- hashExists()
- toute requête SQL
- toute dépendance Eloquent
- toute lecture directe dans question_intents

Le service KLD reçoit les directions déjà existantes via paramètre fourni par l’orchestrateur ou par un provider externe.

===========================================================
CORRECTION 2 — KLD ne fabrique pas les hashes
===========================================================

KEY_LEARNING_DIRECTION ne doit pas décider de l’algorithme de hash.

Donc supprimer du document :

- computeHash()
- sha256()
- génération directe de kld_hash

KLD retourne seulement :

- status : pass / fail
- reason : null ou motif de rejet
- canonical_direction : direction normalisée validée

La génération de kld_hash appartient au futur composant responsable des identifiants du noyau.

===========================================================
CORRECTION 3 — pas d’array anonyme
===========================================================

L’API publique ne doit pas être :

check(array $pair)

Créer un contrat typé interne à la brique.

Nom attendu :
LearningDirectionInput

Fichier attendu :
app/Services/QuestionBank/Rotation/DTO/LearningDirectionInput.php

Champs exacts :
- depth: int
- domainCode: string
- subDomain: string
- subject: string
- dominantIdea: string
- knowledgeFrequency: int
- rotationIdentifier: string|null

KEY_LEARNING_DIRECTION reçoit :

check(
  LearningDirectionInput $input,
  array $existingDirections
): array

existingDirections contient les directions déjà validées, fournies par l’orchestrateur.
