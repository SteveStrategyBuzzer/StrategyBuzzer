## Règles d’architecture non négociables

Node est l’autorité gameplay.

Donc :

* pas de calcul gameplay dans Blade
* pas de transition client autonome
* pas de phase inventée côté client
* pas de stats finales recalculées différemment par Laravel
* Firebase ne doit pas contrôler les phases, le ready, le score, les buzz ou les réponses
* Firebase = présence et WebRTC seulement

## Flow Duo attendu

Le flow cible est :

Lobby
→ READY Socket
→ `phase_changed` Node
→ SYNC initial si nécessaire
→ INTRO
→ Gameplay : Q → R → R → S
→ ROUND_END
→ SYNC uniquement pour relance de ronde / relance structurée
→ manche suivante
→ MATCH_END

Important :
`SYNC` ne doit pas devenir une phase parasite entre chaque petite action.
`SYNC` doit servir à synchroniser une relance de ronde, une transition structurée, ou une reprise contrôlée.

## Logique points / buzzer à vérifier

La règle Duo officielle à auditer :

* Premier joueur à buzzer = joue pour 2 points
* Deuxième joueur à buzzer = joue pour 1 point
* Joueur qui ne buzz pas = joue pour 0 point
* Si joueur à 2 ou 1 points répond faux = -2 points
* Si joueur joue pour 0 point :

  * bonne réponse = 0 point
  * mauvaise réponse = 0 point
* Chaque joueur doit pouvoir avancer à sa vitesse dans la phase réponse, mais Node reste autorité.
* Ne pas afficher de texte qui identifie trop directement “bonne/mauvaise réponse” si la règle UX actuelle l’interdit.
* Le rendu doit indiquer clairement combien le joueur joue : 2, 1 ou 0 point.

À auditer :

* où la position buzzer est stockée
* où le score est calculé
* où les points potentiels sont affichés
* si le score final vient bien de Node
* si les pages lisent les bons champs
