# 1. Corriger immédiatement `confirmConsumed()`

Le flow actuellement implanté est incorrect s’il exécute :

```text
Taxonomy fournit un territoire
↓
fillTaxonomy()
↓
engageBlueprint()
↓
confirmConsumed()
```

`confirmConsumed()` ne doit jamais être appelé immédiatement après `fillTaxonomy()`.

La règle officielle est :

```text
Taxonomy fournit :
subdomain_active
subject_active
dominant_idea_active
↓
KLD vérifie la paire
↓
KEY_STRUCTURE vérifie la structure
↓
KLD = PASS
+
KEY_STRUCTURE = PASS
↓
confirmConsumed() exactement une fois
```

En cas de rejet KLD ou KEY_STRUCTURE :

```text
aucun confirmConsumed()
```

La paire Taxonomy ne doit pas être avancée ni déclarée consommée.

Actions obligatoires :

1. Retire l’appel actuel à `confirmConsumed()` de `KernelPipelineOrchestrator::run()`.
2. Localise le véritable point de sortie PASS de KLD et KEY_STRUCTURE.
3. Place l’appel à `confirmConsumed()` uniquement après les deux validations réussies.
4. Rends cet appel idempotent.
5. Ajoute les tests suivants :

   * territoire fourni, KLD PASS, KS PASS → consommation une fois ;
   * KLD FAIL → aucune consommation ;
   * KS FAIL → aucune consommation ;
   * répétition du signal PASS → aucune double consommation.

Ne crée pas une fausse validation PASS pour faire avancer le test.

Si KLD ou KEY_STRUCTURE ne sont pas encore implantés, ne simule pas leur logique métier dans KRP. Crée uniquement un contrat d’intégration explicite et déclare le raccordement terminal BLOQUÉ par leur absence.

# 6. Déclencher réellement le Blueprint suivant

Après un `CURRENT_KERNEL_RECEIVED` traité avec succès :

```text
comptabilisation idempotente
↓
autorisation du Blueprint suivant
↓
KernelBlueprintFactory
↓
KernelPipelineOrchestrator
```

Le listener ou le processeur Outbox doit réellement provoquer l’itération suivante.

La logique doit être idempotente :

* si le reçu n’existe pas :

  * créer le reçu ;
  * incrémenter le compteur une fois ;
* si le reçu existe déjà :

  * ne pas incrémenter une seconde fois ;
* si l’événement n’est pas encore marqué traité :

  * vérifier que le Blueprint suivant existe ou le créer ;
* `KernelBlueprintFactory` doit empêcher deux Blueprints actifs.

L’événement Outbox doit être marqué traité uniquement lorsque :

* la comptabilisation est sûre ;
* la création ou la récupération idempotente du Blueprint suivant est terminée ;
* KRP a produit `ROTATION_ASSIGNED` ou `PRODUCTION_ON_HOLD`.

Ajoute les tests :

1. réception normale → compteur +1 → Blueprint suivant créé ;
2. même événement rejoué → compteur inchangé → aucun deuxième Blueprint ;
3. échec après comptabilisation mais avant création suivante → rejeu complète la création sans double compteur ;
4. aucun besoin restant → `PRODUCTION_ON_HOLD` ;
5. événement déjà traité → `NO-OP`.
