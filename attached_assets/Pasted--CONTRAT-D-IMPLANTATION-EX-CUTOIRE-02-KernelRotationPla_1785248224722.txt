# 2. Décisions techniques fermant les bloquants

## 2.1 Créateur technique du KernelBlueprint

Le composant technique responsable du flow est :

```text
KernelPipelineOrchestrator
```

Il ne prend aucune décision métier de rotation.

Il orchestre uniquement les appels dans l’ordre officiel.

La création de l’enveloppe appartient à :

```text
KernelBlueprintFactory
```

Flow :

```text
KernelPipelineOrchestrator
↓
KernelBlueprintFactory::create()
↓
KernelBlueprint vide
↓
KernelRotationPlanner
```

### Responsabilités de KernelBlueprintFactory

* créer une nouvelle instance vide du KernelBlueprint ;
* attribuer son identité canonique ;
* créer son enregistrement d’exécution ;
* ne remplir aucun slot métier ;
* ne sélectionner aucun Depth ;
* ne sélectionner aucun Domaine.

### Responsabilités de KernelPipelineOrchestrator

* demander la création du Blueprint ;
* transmettre le Blueprint à KRP ;
* transmettre le résultat KRP à Taxonomy ;
* gérer la boucle immédiate lorsque Taxonomy transmet `EMPTY` ;
* engager le Blueprint dans le reste du pipeline lorsque Taxonomy fournit son territoire ;
* ne jamais décider lui-même du Depth ou du Domaine.

---

## 2.2 Identité canonique du Blueprint

L’identité canonique est :

```text
blueprint_id
```

Format obligatoire :

```text
UUIDv7
```

Règles :

* généré par `KernelBlueprintFactory` ;
* généré avant l’entrée dans KRP ;
* immuable pendant tout le pipeline ;
* distinct de `kernel_code` ;
* distinct de `rotation_identifier` ;
* distinct du Depth ;
* distinct du Domaine ;
* transmis jusqu’à ReadyBank ;
* inclus dans `CURRENT_KERNEL_RECEIVED`.

`rotation_identifier` est supprimé du nouveau contrat.

`kernel_code` ne peut pas servir d’identité du Blueprint, puisqu’il est écrit plus tard par son moteur propriétaire.

---

## 2.3 Cycle de vie d’exécution du Blueprint

Les états suivants sont des états techniques d’orchestration.

Ils ne sont pas des slots du KernelBlueprint et ne sont pas des verdicts de validation.

```text
CREATED_UNENGAGED
ENGAGED_IN_PIPELINE
READY_BANK_RECEIVED
NOT_ENGAGED_PRODUCTION_ON_HOLD
```

### CREATED_UNENGAGED

Le Blueprint vient d’être créé.

Il peut encore :

* recevoir plusieurs propositions `depth + domain` ;
* être réutilisé après un ou plusieurs `EMPTY` ;
* être engagé dans le pipeline ;
* être arrêté avant engagement si aucun besoin ne reste.

### ENGAGED_IN_PIPELINE

Taxonomy a fourni :

* `subdomain_active` ;
* `subject_active` ;
* `dominant_idea_active`.

À partir de ce moment :

* le couple `depth + domain` est définitivement engagé ;
* il ne peut plus être remplacé ;
* le Blueprint poursuit le pipeline intellectuel.

### READY_BANK_RECEIVED

ReadyBank a reçu le Blueprint terminé.

Cet état provoque l’émission de :

```text
CURRENT_KERNEL_RECEIVED
```

### NOT_ENGAGED_PRODUCTION_ON_HOLD

KRP constate qu’aucun Depth ne possède encore :

```text
cycle_completed[depth] < cycle_target[depth]
```

Alors :

* aucun `depth + domain` n’est engagé ;
* le Blueprint ne poursuit pas le pipeline ;
* aucun noyau n’est comptabilisé ;
* aucun signal ReadyBank n’est produit ;
* l’enveloppe est conservée uniquement comme trace technique non engagée ;
* elle ne devient jamais un noyau canonique de ReadyBank.

Cette décision ferme `OUVERT_1`.

# 3. Un seul Blueprint actif

À tout instant, il ne peut exister qu’un seul Blueprint dans l’un de ces états actifs :

```text
CREATED_UNENGAGED
ou
ENGAGED_IN_PIPELINE
```

Cette protection appartient au registre technique des exécutions du Blueprint.

Elle ne doit pas être représentée par un booléen dans `RotationState`.

Avant de créer une nouvelle enveloppe, `KernelBlueprintFactory` vérifie qu’aucun Blueprint actif n’existe.

Le nouveau Blueprint est autorisé après :

```text
CURRENT_KERNEL_RECEIVED
```

ou lorsqu’un Blueprint précédent a été classé :

```text
NOT_ENGAGED_PRODUCTION_ON_HOLD
```

# 4. Tour de Depth

## 4.1 Mission

Le mécanisme `Tour de Depth` répond uniquement à la question :

```text
Quels Domaines participent encore
au Tour de Depth actif ?
```

## 4.2 Domaines officiels

```text
Géographie
Histoire
Faune
Art
Sport
Cinéma
Cuisine
Science
```

`Général` est exclu de la création.

## 4.3 Initialisation

Au début de chaque Tour de Depth :

```text
Géographie = ON
Histoire   = ON
Faune      = ON
Art        = ON
Sport      = ON
Cinéma     = ON
Cuisine    = ON
Science    = ON
```

## 4.4 Territoire fourni

Lorsque Taxonomy fournit son territoire :

```text
subdomain_active
subject_active
dominant_idea_active
```

alors :

```text
Domaine reste ON
```

Aucun signal `AVAILABLE` n’existe.

## 4.5 EMPTY

Lorsque Taxonomy transmet :

```text
EMPTY
```

alors :

```text
Domaine ON
↓
Domaine OFF
↓
Domaine ignoré pendant le reste du Tour de Depth
```

Un Domaine déjà `OFF` ne peut pas produire une deuxième transition.

La transition doit être idempotente.

## 4.6 Fermeture

```text
8 Domaines OFF
↓
Tour de Depth terminé
```

# 5. DepthNeedMatrix

## 5.1 Mission

DepthNeedMatrix porte :

* les cibles de Tours de Depth ;
* les Tours réellement complétés ;
* la progression numérique du tour actif ;
* les noyaux réellement reçus.

Elle ne porte pas l’identité des Domaines `ON/OFF`.

## 5.2 DepthCycle officiel

```text
2 → 4 → 6 → 7 → 8 → 9 → 10
```

Après Depth 10, la recherche reprend à Depth 2.

## 5.3 Cibles officielles

```text
cycle_target[2]  = 250
cycle_target[4]  = 300
cycle_target[6]  = 350
cycle_target[7]  = 350
cycle_target[8]  = 350
cycle_target[9]  = 250
cycle_target[10] = 100
```

## 5.4 Progression du Tour de Depth actif

```text
0/8 → 1/8 → 2/8 → … → 8/8
```

Chaque nouvelle transition valide :

```text
ON → OFF
```

produit exactement :

```text
+1/8
```

## 5.5 Fermeture d’un tour

À `8/8` :

```text
cycle_completed[active_depth] += 1
```

Puis DepthNeedMatrix recherche le prochain Depth suivant dans le cycle dont :

```text
cycle_completed[depth] < cycle_target[depth]
```

Le résultat est retourné à KRP.

KRP applique ce résultat comme nouveau `active_depth`.

## 5.6 Noyaux reçus

La source de vérité est :

```text
kernel_received_total[depth][domain]
```

À chaque `CURRENT_KERNEL_RECEIVED` valide :

```text
kernel_received_total[depth][domain] += 1
```

Le total du Depth est calculé :

```text
kernel_received_total[depth]
=
somme des huit Domaines
```

Aucun second compteur total ne doit être persisté.

# 6. KernelRotationPlanner

## 6.1 Entrée principale

```text
KernelBlueprint vide
+
contexte de rotation
```

Le contexte peut contenir :

```text
previous_domain
```

Il provient :

* du Domaine déjà inscrit dans le même Blueprint lors d’un `EMPTY` ;
* du Domaine porté par `CURRENT_KERNEL_RECEIVED` pour le Blueprint suivant ;
* de `null` au tout premier lancement d’un Tour de Depth.

Cela évite tout :

```text
domain_position
current_domain_index
```

## 6.2 Sorties possibles

```text
ROTATION_ASSIGNED
PRODUCTION_ON_HOLD
```

### ROTATION_ASSIGNED

KRP a écrit :

```text
depth
domain
```

dans le Blueprint.

### PRODUCTION_ON_HOLD

Aucun Depth ne possède encore de besoin.

Le Blueprint passe à :

```text
NOT_ENGAGED_PRODUCTION_ON_HOLD
```

## 6.3 Sélection du Domaine

DomainCycle officiel :

```text
Géographie
→ Histoire
→ Faune
→ Art
→ Sport
→ Cinéma
→ Cuisine
→ Science
→ retour à Géographie
```

KRP :

1. part du Domaine précédent ;
2. parcourt l’ordre officiel ;
3. ignore les Domaines `OFF` ;
4. sélectionne le prochain Domaine `ON`.

Aucun curseur numérique n’est persisté.

## 6.4 Écriture dans le Blueprint

KRP écrit uniquement :

```text
depth
domain
```

Avant engagement dans le pipeline, ce couple est provisoire.

Sur `EMPTY`, KRP peut remplacer ce couple dans le même Blueprint.

Dès que Taxonomy remplit ses trois slots, le couple devient engagé et immuable.

# 9. Canal ReadyBank → KRP

Le canal officiel est un événement transactionnel avec Outbox.

Nom de l’événement :

```text
CURRENT_KERNEL_RECEIVED
```

## 9.1 Production de l’événement

Dans la même transaction que la réception ReadyBank :

1. ReadyBank persiste le Blueprint ;
2. l’exécution du Blueprint passe à `READY_BANK_RECEIVED` ;
3. ReadyBank écrit un événement dans l’Outbox ;
4. la transaction est validée.

## 9.2 Payload obligatoire

```text
event_id
event_type = CURRENT_KERNEL_RECEIVED
schema_version = 1
blueprint_id
depth
domain
occurred_at
```

`kernel_code` peut être présent pour la traçabilité, mais KRP ne l’utilise pas pour l’idempotence.

## 9.3 Consommation

Un listener dédié consomme l’événement :

```text
ApplyCurrentKernelReceivedToRotation
```

Il :

1. vérifie `blueprint_id` ;
2. tente de créer un reçu idempotent ;
3. si le reçu existe déjà, n’incrémente rien ;
4. sinon incrémente :
   `kernel_received_total[depth][domain] += 1` ;
5. autorise la création du Blueprint suivant ;
6. marque l’événement Outbox comme traité.

Cette décision ferme `OUVERT_3`.

# 11. Atomicité obligatoire

## Transition EMPTY

Dans une seule transaction :

1. verrouiller `kernel_rotation_state_v2` ;
2. vérifier que le Domaine est `ON` ;
3. le passer à `OFF` ;
4. incrémenter `empty_progress_current_tour` ;
5. si progression = 8 :

   * incrémenter `cycle_completed[active_depth]` ;
   * sélectionner le prochain Depth requis ;
   * créer le nouveau Tour de Depth ;
   * remettre les huit Domaines à `ON` ;
   * remettre la progression à `0/8` ;
6. persister ;
7. libérer la transaction.

Un signal `EMPTY` répété pour un Domaine déjà `OFF` est un `NO-OP`.

## CURRENT_KERNEL_RECEIVED

Dans une seule transaction :

1. tenter d’insérer le reçu par `blueprint_id` ;
2. si le reçu existe déjà :

   * aucun incrément ;
3. sinon :

   * incrémenter `kernel_received_total[depth][domain]` ;
4. valider la transaction.
