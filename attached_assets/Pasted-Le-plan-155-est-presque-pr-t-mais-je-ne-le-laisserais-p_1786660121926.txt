Le plan #155 est presque prêt, mais je ne le laisserais pas coder tel quel. Il contient 4 corrections nécessaires, dont trois peuvent produire une architecture fausse.

1. BLOQUANT — CURRENT_KERNEL_RECEIVED doit toujours compter le noyau reçu

Le LOT B-3 propose en substance :

si pending_depth_exhausted_depth == null
→ incrémenter kernel_received

sinon
→ changer de Depth / PRODUCTION_ON_HOLD

C’est faux.

Même si DEPTH_EXHAUSTED a été signalé, le Blueprint courant vient quand même d’arriver dans ReadyBank. Donc son CURRENT_KERNEL_RECEIVED doit être comptabilisé avant d’appliquer la transition prospective.

La séquence doit être :

CURRENT_KERNEL_RECEIVED
↓
idempotence par blueprint_id
↓
kernel_received_total +1
pour le Depth + Domaine DU BLUEPRINT REÇU
↓
puis vérifier le signal DEPTH_EXHAUSTED mémorisé
↓
si aucun :
    rotation normale
si Depth 2/4/6/7/8/9 épuisé :
    préparer prochain Depth
si Depth 10 épuisé :
    PRODUCTION_ON_HOLD

DEC-093 doit rester vrai dans tous les cas.

2. BLOQUANT — domain_states est écrit mais jamais utilisé pour choisir le prochain domaine

LOT B prévoit :

receiveDomainExhausted()
→ domain_states[depth][domain] = DOMAIN_EXHAUSTED

Mais le sélecteur actif reste basé sur l’ancien DepthTourState/tour_domain_states.

Donc KRP pourrait recevoir :

DOMAIN_EXHAUSTED(2, faune)

et continuer plus tard à sélectionner Faune.

Le LOT B doit également implanter le sélecteur KRP v3.2 :

active_depth
+
domain_position
+
domain_states[active_depth]
↓
chercher le prochain domaine dans DomainCycle
qui n'est PAS DOMAIN_EXHAUSTED

Exemple :

GE → HI → FA → AR...

si :

FA = DOMAIN_EXHAUSTED

alors :

GE → HI → AR → SP...

Sans ça, le récepteur DOMAIN_EXHAUSTED ne sert à rien.

3. BLOQUANT — peekNext() == null ne signifie PAS DOMAIN_EXHAUSTED

Cette phrase du LOT C doit être supprimée :

peekNext()->null
→ Taxonomy signale DOMAIN_EXHAUSTED

Nous avons précisément verrouillé le contraire.

DOMAIN_EXHAUSTED existe seulement lorsque Taxonomy sait réellement que son réservoir est épuisé après consommation exacte.

Un null technique peut éventuellement signifier autre chose :

réservoir pas encore préparé
erreur
état intermédiaire
absence temporaire
autre comportement défini par 03_Taxonomy

KRP n’a pas le droit d’en déduire l’épuisement.

Le futur contrat doit être :

Taxonomy
↓
consommation exacte
↓
recalcul réel du réservoir
↓
si réellement épuisé :
DOMAIN_EXHAUSTED explicite

Donc aucune conversion automatique null = exhausted.

4. MAJEUR — conflit de signal ne doit pas devenir un NO-OP silencieux

Le plan dit :

receiveDepthExhausted(4)

puis si pending_depth_exhausted_depth déjà non-null
→ NO-OP

Ça marche uniquement si c’est le même signal.

Correct :

pending = null
receiveDepthExhausted(4)
→ pending = 4

receiveDepthExhausted(4)
→ NO-OP idempotent

Mais :

pending = 4
receiveDepthExhausted(6)

ne doit surtout pas devenir NO-OP.

C’est une incohérence.

Il faut :

même valeur
→ NO-OP idempotent

valeur différente
→ REFUS / exception d'invariant

Même principe pour les signaux : valider Depth supporté, Domaine officiel et cohérence avec le contexte de rotation attendu.

Correction supplémentaire de migration

Je corrigerais aussi A-4. Ceci :

ADD depth_state
BACKFILL
DROP rotation_status

dans la même migration n’est pas réellement une « migration additive ».

Plus sûr :

Migration 1
→ ADD depth_state
→ backfill

patch code
→ tous readers/writers utilisent depth_state

tests
→ validation

Migration cleanup ultérieure
→ DROP rotation_status

Même principe pour les anciennes colonnes : ne pas réécrire une ancienne migration déjà appliquée juste pour ajouter un commentaire historique.
