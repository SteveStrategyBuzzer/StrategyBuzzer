# ERREURS RESTANTES À ALIGNER

## 1. GAME_SERVER_URL incorrect dans les vues gameplay
Bug systémique confirmé :
plusieurs vues gameplay utilisent encore :

window.GAME_SERVER_URL = window.location.origin

C’est faux.
Cela pointe vers Laravel/Nginx et non vers le game server Socket.IO.

Conséquence :
- l’intro ne reçoit pas correctement le gameplay live
- la question/réponse ne peuvent pas se connecter correctement au game server
- le flow reste bloqué même si le serveur avance

À corriger dans toutes les vues gameplay concernées, au minimum :
- resources/views/game_intro.blade.php
- resources/views/duo_question.blade.php
- resources/views/duo_answer.blade.php

Je veux que ces vues utilisent la même logique correcte que le lobby, ou mieux :
une injection centralisée propre provenant de Laravel / layout, sans duplication incohérente.

## 2. Lobby contient encore un countdown overlay local
Bug confirmé :
le lobby contient encore un overlay avec “3”.

C’est interdit dans l’architecture actuelle.

Le lobby ne doit pas lancer un countdown local ni afficher un faux start local.
Le serveur décide les phases.

À faire :
- supprimer le countdown overlay local du lobby
- supprimer toute logique locale liée à ce countdown
- conserver uniquement la navigation pilotée par phase serveur

## 3. Navigation lobby → intro doit être Socket-driven
Le comportement attendu est :

phase_changed: INTRO
→ redirection vers /game/duo/intro

Je ne veux plus d’overlay local de remplacement.
Je veux une vraie transition de page vers l’intro.

## 4. Intro doit rester un écran passif piloté par Node
game_intro.blade.php doit :
- afficher Ladies & Gentlemen
- afficher les avatars / thème / infos
- écouter phase_changed / QUESTION_ACTIVE
- rediriger vers la question quand le serveur le décide

Il ne doit PAS :
- utiliser Firebase pour le start
- utiliser setTimeout pour décider du start
- utiliser une logique autonome
