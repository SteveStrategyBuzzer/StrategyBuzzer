# CONTRAT BLUEPRINT À RESPECTER

Le Kernel Blueprint est un objet de description, de stockage et de références métier textuelles non exécutables.

Il définit la structure officielle d’un noyau.

Il contient les slots officiels du noyau.

Chaque slot doit contenir :

* une valeur, si elle existe ;
* un contrat `slot_reference` ;
* des références métier textuelles servant de guide aux briques suivantes.

Les références métier du Blueprint sont :

* prescriptives ;
* non exécutables.

Le Blueprint ne choisit rien.

Il ne calcule rien.

Il ne valide rien.

Il ne génère aucun contenu.

Il ne déduit aucune valeur.

Il stocke seulement ce que les briques autorisées produisent selon leur contrat.

---

# FORMAT OFFICIEL D’UN SLOT_REFERENCE

Chaque `slot_reference` doit utiliser exactement ces 11 champs :

```yaml
slot_reference:
  purpose:
  authority:
  producer:
  value_source:
  stored_value:
  readable_by:
  consumed_by:
  lifecycle:
  constraints:
  forbidden:
  dependencies:
```

Ne pas ajouter de champ.

Ne pas supprimer de champ.

Ne pas renommer de champ.

# CORRECTIONS BLUEPRINT OBLIGATOIRES

Dans le code réel du Blueprint, corriger uniquement les éléments suivants :

## 1. Supprimer les anciennes références interdites

Supprimer ou remplacer toute référence qui associe la rotation à :

```text
yy-xx
kernel_code_prefix
préfixe kernel_code
KernelRotationPlanner(yy-xx)
```

Ces notions sont interdites pour la phase Blueprint actuelle.

---

## 2. Remplacer par la notion officielle

La notion officielle est :

```text
rotation_identifier
```

Règles :

```text
rotation_identifier n’est pas kernel_code.
rotation_identifier n’est pas kernel_code_prefix.
rotation_identifier n’est pas un fragment garanti du futur kernel_code.
rotation_identifier n’a aucun format imposé dans ce contrat.
rotation_identifier sert uniquement à identifier une rotation.
```

---

## 3. Ajouter le slot `rotation_identifier`

Ajouter `rotation_identifier` au Blueprint uniquement si le slice réel confirme l’emplacement naturel des slots.

Le slot doit respecter ce contrat :

```yaml

    purpose: "Identifiant unique de la rotation."

      - "KLD"
      - "QuestionIntent"
      - "Audit"
    consumed_by:
      - "KEY_STRUCTURE"
      - "KLD"
    lifecycle: "EMPTY -> FILLED -> LOCKED"

      - "Unique dans le périmètre de rotation."
      - "Aucun format imposé dans ce contrat."
      - "Ne doit jamais être traité comme kernel_code."
      - "Ne doit jamais être traité comme kernel_code_prefix."

      - "Utiliser comme kernel_code."
```
