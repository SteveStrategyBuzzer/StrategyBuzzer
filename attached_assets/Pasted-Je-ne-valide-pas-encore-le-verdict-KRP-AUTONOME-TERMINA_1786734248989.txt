Ce qui bloque encore

1. T-PG-03 ne prouve pas encore l'exactly-once du vrai CKR concurrent.

Le rapport dit :

UNIQUE(blueprint_id) rejette le deuxième INSERT.

Ce n'est pas suffisant. Deux vrais appels concurrents à :

KernelRotationPlanner::receiveKernelReceivedV2()

doivent produire :

1 succès métier
+
1 NO-OP idempotent
+
0 PDOException exposée
+
1 receipt
+
kernel_received_total +1 exactement une fois

Sinon il existe encore une race :

Worker A vérifie absence receipt
Worker B vérifie absence receipt
A INSERT
B INSERT
→ UNIQUE violation

La contrainte DB protège les données, mais elle ne prouve pas que l'API KRP est idempotente sous concurrence.

2. T-PG-06 et T-PG-07 doivent être de vrais appels concurrents.

« Deux appels identiques » ne suffit pas s'ils sont séquentiels.

Il faut deux connexions/processus réellement simultanés contre Neon.

3. T-PG-08 ne teste pas le vrai chemin KRP.

Le rapport dit essentiellement :

SAVEPOINT
→ INSERTs manuels
→ ROLLBACK TO SAVEPOINT

Ça prouve PostgreSQL.

Ça ne prouve pas :

KernelPipelineOrchestrator
→ FOR UPDATE
→ resolveNextRotation
→ Factory::create
→ applyRotation
→ erreur
→ rollback

Le test terminal doit passer par le code réel.

4. T-PG-09 n'est pas le test “rollback après fillRotation”.

T-PG-09 fait :

transaction KRP
→ COMMIT
→ Taxonomy
→ exception
→ Blueprint durable

C'est une excellente preuve réelle de IMPASSE-KRP-001.

Mais ce n'est pas :

fillRotation
→ erreur AVANT COMMIT KRP
→ rollback

Les deux tests sont différents.
