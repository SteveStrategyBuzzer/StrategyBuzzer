3. LES 4 POINTS À CLARIFIER OBLIGATOIREMENT
========================================

----------------------------------------
POINT A — GAME HEADER : QUI CONSTRUIT QUOI
----------------------------------------

Je ne valide pas un header totalement vide rempli uniquement par JS.

Je veux une règle claire :
- Laravel rend la base
- GameplayRuntime.js met à jour le temps réel

Tu dois préciser noir sur blanc ce qui est injecté par Laravel au rendu initial, et ce qui est ensuite mis à jour par JS.

### Données de base que Laravel doit continuer à injecter
Je veux que tu raisonnes explicitement avec cette liste :

#### Côté joueur courant
- player id
- player display name
- player avatar path
- score initial
- strategic avatar name
- strategic avatar path
- skills disponibles
- état initial utile déjà connu côté rendu

#### Côté adversaire
- opponent id
- opponent display name
- opponent avatar path
- score initial
- état initial utile déjà connu côté rendu

#### Côté match / session
- match_id
- room_id
- lobby_code
- jwt_token
- question index initial ou compteur initial si disponible
- round initial si disponible
- total_questions si disponible
- URLs nécessaires (answer, result, waiting, resume, etc.)

#### Côté phase
- phase initiale déjà connue au rendu si disponible
- flags initiaux nécessaires à l’affichage sécurisé

### Ce que GameplayRuntime.js peut mettre à jour ensuite
- score en temps réel
- phase en temps réel
- indicateurs de connexion
- affichage cerveau / loading / transition
- compteurs visuels liés à l’état Node
- badges d’état joueur / adversaire
- données dérivées d’un event Socket
- changement de question/round lorsque Node les fournit

### Ce que je ne veux pas
Je ne veux pas que GameplayRuntime.js reconstruise toute l’identité de base du joueur/adversaire en partant de zéro, si Laravel peut déjà fournir ces données au rendu.
Je veux une base Blade stable, enrichie et mise à jour par JS.

Tu dois donc me donner un tableau précis :
- élément
- rendu initial par Blade
- mis à jour ensuite par GameplayRuntime.js
- jamais géré par JS seul au premier rendu

POINT D — TIMERS LOCAUX : INTERDICTION + EXCEPTIONS ÉVENTUELLES
----------------------------------------

Je ne valide pas la phrase “timers locaux tolérés”.
C’est trop flou et trop dangereux.

La règle doit être :

### interdit par défaut
Aucun timer local qui décide :
- du démarrage réel d’une phase
- de la fin réelle d’une phase
- de la logique de transition gameplay
- de la synchronisation entre joueurs

### autorisé uniquement comme affichage local
Un timer local peut servir à :
- interpolation visuelle
- animation UI
- countdown purement visuel dérivé d’un phaseEndsAtMs serveur
- micro-animation
- CSS/JS d’habillage

Mais jamais comme source décisionnelle.

### Si tu veux une exception tiebreaker
Tu dois la justifier précisément, phase par phase :
- quelle vue
- quel timer
- pourquoi il n’entre pas en conflit avec Node
- pourquoi il n’est qu’un affichage
- pourquoi il ne recrée pas un désalignement

Je veux donc une réponse explicite :
- règle générale
- exceptions éventuelles
- pourquoi elles sont sûres
- comment elles sont encadrées

4. RAPPEL DES CONSÉQUENCES SI CE N’EST PAS FAIT PROPREMENT
========================================

Je veux que tu prennes très au sérieux les conséquences si ces 4 points restent flous.

### Si le header est trop JS-driven
Conséquences :
- flash de contenu vide au chargement
- rechargements fragiles
- dépendance excessive au runtime
- régressions plus dures à diagnostiquer
- plus de complexité inutile

### Si Socket.IO n’est pas centralisé proprement
Conséquences :
- doubles connexions
- doubles joinRoom
- doubles handlers
- score affiché deux fois
- redirections incohérentes
- bugs intermittents très difficiles à traquer
- régression du Duo stabilisé

### Si le cerveau n’est pas strictement Node-driven
Conséquences :
- décalages visuels entre joueurs
- cerveau qui apparaît ou disparaît au mauvais moment
- logique locale qui redevient maître au lieu de Node
- retour du faux countdown déguisé
- rupture de synchronisation

### Si les timers locaux restent flous
Conséquences :
- phases désynchronisées
- effets incohérents entre devices
- comportement différent selon latence ou device
- bugs tiebreaker difficiles à reproduire
- dette technique immédiate
